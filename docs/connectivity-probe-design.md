# 数据源连通性复检设计说明

## 1. 背景与目标

数据集负责人启用分析数据集前，必须确认所属数据源真实可连通。原实现只展示「启用状态」，
连接失败要等到数据集刷新时才暴露。本次改造为数据源连接增加**连通性复检**，并把
最近一次成功、失败原因、探测时间持久化；复检未通过的数据源不能被新建或启用的数据集引用。

## 2. 连通规则（不满足规则的连接不允许保存）

规则集中声明在 `app/rules.py`，通过 `GET /api/datasource/rules` 对外暴露，前后端共用一份口径。

| 规则项 | 标准 |
| --- | --- |
| 数据库类型标准 | 仅支持 MySQL、PostgreSQL、Oracle、SQLServer、ClickHouse |
| 探测超时阈值 | 1~10 秒，默认 5 秒 |
| 连接池可用范围 | 1~100，默认 10 |
| 连接地址 | 必须为 `主机名或IP:端口`，端口 1~65535 |
| 默认库名 | 必填，标识符规范 `^[A-Za-z_][A-Za-z0-9_]{0,63}$` |
| 认证凭据 | 用户名/密码不得为空 |
| 探活模式 | 真实 / 模拟 |

`validate_connection()` 一次性返回全部违规说明，`create_entry` / `update_entry` 在落库前强制校验，
任一规则不通过即拒绝保存。

## 3. 探活方式与失败分级

探活引擎 `app/probe.py` 把一次复检拆成四个顺序阶段，任一阶段失败即终止并记录**失败阶段**：

1. **配置预检**（BLOCKER）：复用保存规则，非法配置不进入真实探测；
2. **网络建连**（BLOCKER）：真实模式下对 `主机:端口` 发起 TCP 拨号
   （`socket.create_connection`，受超时阈值约束），覆盖超时、DNS 失败、连接拒绝；
3. **身份认证**（CRITICAL）：密码失效 / 账号锁定在此暴露；
4. **默认库校验**（MAJOR）：默认库不存在或账号无权限。

失败分级：`BLOCKER > CRITICAL > MAJOR > MINOR`（MINOR 为保留分级）。
任一失败级别都判定复检不通过并阻断数据集引用。结果始终附带**数据库类型、默认库名、失败阶段、
失败原因、耗时、超时阈值**，而不是一个笼统的不可用标记。

### 探活模式

- **真实模式**：执行真实 TCP 拨号；认证与库校验在接入 DB-API 驱动后替换为
  `connect` / `SELECT 1` / 库目录查询，阶段与分级口径不变。
- **模拟模式**：无数据库实例的环境跳过拨号，用凭据/地址中的确定性标记复现故障，
  保证「密码失效 → 恢复」业务场景可复跑、可测试：
  - 凭据含 `__fail_auth__` → 身份认证失败（CRITICAL）
  - 凭据含 `__fail_catalog__` → 默认库校验失败（MAJOR）
  - 地址含 `__fail_network__` → 网络不可达（BLOCKER）

## 4. 持久化与重复提交

- 仓库 `app/store.py` 在内存表之外增加 JSON 快照（默认 `backend/data/workbench_store.json`，
  可用环境变量 `WORKBENCH_STORE_PATH` 覆盖，置空关闭落盘）。每次写操作原子落盘，启动优先回放。
- 新增 `probe_history` 表：**同一连接只保留最近一次有效结果**，重复复检不堆积历史。
- 数据源行上持久化：复检结论、失败分级/阶段/原因、最近成功探测时间、最近探测时间、轮次、耗时。
  最近成功探测时间是历史事实，连接参数变更或后续失败都不会抹掉它。
- **重复提交合并**：`DatasourceService.probe` 按连接维护在途字典（锁 + 条件变量）。
  同一连接并发复检时，首个请求成为执行者并生成轮次，其余请求阻塞等待并复用同一轮结果，
  只产生一次有效探测与一条历史。串行（无重叠）复检各自成轮，属正常语义。

## 5. 依赖清单联动（核心场景）

数据集通过 `依赖数据源连接编号` 绑定数据源。复检落库时 `_sync_dependents` 把同一轮快照
（结论、分级、阶段、原因、最近成功时间、探测时间、轮次）同步给**全部**依赖数据集，并切换
`可刷新` 闸门：

- 复检失败：所有依赖数据集 `可刷新=false`，但**状态不变、仍可查看**，刷新动作被拒绝；
- 复检恢复：同一轮结果把所有依赖数据集一起恢复为 `可刷新=true`。

典型链路（DS-001、DS-004 共用 DBC-0003）：

1. MySQL 密码失效 → 复检在「身份认证」阶段失败（CRITICAL）；
2. DS-001、DS-004 同时显示不可刷新，保留最近成功探测时间，仍可查看；
3. 密码恢复后再次复检通过，两个数据集在**同一轮**恢复可刷新。

## 6. 两个业务面的闸门

### 数据源面（`/api/datasource`）

- `POST /{id}/probe` 发起复检；`GET /{id}/probe-history` 查最近一次结果；
- `POST /{id}/actions` 启用配置时，复检结论非「通过」一律拒绝。

### 数据集面（`/api/dataset`）

- 新建：绑定的数据源不存在或复检未通过，拒绝保存；
- 启用：再次校验数据源复检结论，未通过不允许启用；
- 刷新（新增动作 `刷新数据集`）：仅当 `可刷新=true` 放行，否则回传失败原因与最近成功探测时间；
- 列表支持 `refreshable=true/false` 过滤，前端启用/刷新按钮在数据源不健康时禁用。

## 7. 接口清单

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/datasource/rules` | 连通规则与允许保存条件 |
| GET | `/api/datasource` | 列表，支持 keyword/status/probe_result |
| GET | `/api/datasource/{id}` | 连接明细 |
| POST | `/api/datasource` | 登记连接（规则校验，不通过拒绝保存） |
| PUT | `/api/datasource/{id}` | 更新连接（变更后历史结论作废） |
| POST | `/api/datasource/{id}/probe` | 连通性复检（并发合并） |
| GET | `/api/datasource/{id}/probe-history` | 最近一次复检结果 |
| POST | `/api/datasource/{id}/actions` | 提交校验/启用/停用（启用受复检闸门） |
| GET | `/api/dataset` | 列表，支持 keyword/status/refreshable |
| POST | `/api/dataset` | 新建数据集（数据源必须复检通过） |
| POST | `/api/dataset/{id}/actions` | 提交校验/启用/停用/**刷新数据集** |

## 8. 测试

后端 28 个 unittest 用例（`backend/tests/`，仅依赖标准库）覆盖：规则边界、四阶段失败分级、
真实 TCP 拨号失败、密码失效/恢复全链路、两数据集同轮联动、新建/启用/刷新闸门、
探测历史去重、并发复检合并、快照持久化字段。

运行：

```bash
cd backend
WORKBENCH_STORE_PATH= .venv/bin/python -m unittest discover -s tests
```
